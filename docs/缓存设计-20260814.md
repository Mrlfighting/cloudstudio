# 图片平台二级缓存设计文档（2026-08-14）

> 本文件为公共图库平台「本地缓存(L1) 优先、Redis(L2) 次之」二级缓存方案的完整设计文档，随 `feature/cache-module` 分支交付。

## 一、背景与目标

公共图库平台随着图片数据量增长，列表/详情查询直接压 PostgreSQL，`sort=popularity` 排序与关键词搜索（JSONB `@>` + ilike）代价高。引入二级缓存以降低数据库压力、提升读性能。

**已确认的决策**：① 只缓存元数据、不缓存二进制（下载保持 COS 302 重定向）；② L1 用 `cachetools`；③ 热key探测用「惰性计数提升」（不依赖后台任务）；④ `download_count` 用短 TTL + 失效协调。

## 二、总体架构

```
请求 → Service 层
        └─ @cached 装饰器 / get_or_load(key, loader)
             ├─ 1) 查 L1 本地内存(cachetools.TTLCache)  ——命中返回
             ├─ 2) 未命中 → 查 L2 Redis(redis.asyncio DB0) ——命中回填 L1 返回
             └─ 3) 未命中 → loader() 查 PostgreSQL → 回填 L2+L1 返回
写操作(upload/update/audit/delete) → evict(detail) + invalidate_by_prefix("pic:list:")
```

- **L1**：进程内 `MemoryBackend`（`cachetools.TTLCache`，线程安全、全局 TTL + maxsize）
- **L2**：复用现有 `RedisBackend`（JSON 序列化，`set` 支持 `ex=ttl`）
- **降级**：Redis 异常 → try/except 跳过 L2，只走 L1 + DB 直读并回填 L1，`logger.warning` 告警（fail-open）

## 三、缓存 Key 设计

命名规范：`pic:{类型}:{维度...}`，统一前缀 `pic:` 便于归类与 `invalidate_by_prefix` 批量失效。

| 场景 | Key 模板 | 示例 |
|---|---|---|
| 列表 | `pic:list:{scope}:{category}:{sort}:{page}:{size}:{kw8}` | `pic:list:public:all:time:1:20:-` |
| 详情 | `pic:detail:{picture_id}` | `pic:detail:123` |
| 热key计数 | `pic:hot:{picture_id}` | `pic:hot:123`（值=窗口内计数，TTL=窗口） |

- `scope` ∈ `public`（用户端已发布）/ `my` / `manage`（后两者默认不缓存）
- `category` 空值用 `all` 占位；`sort` ∈ `time` / `popularity`
- `kw8`：关键词 `md5(keyword)[:8]` 压缩，无关键词用 `-`；纯枚举/数字维度直接拼接保证可读性

## 四、缓存 Value 设计

**只缓存元数据（结构化 JSON），二进制仍走 COS 302**。

| 场景 | 序列化 | 结构 |
|---|---|---|
| 列表 | JSON | `{"data":[PictureListItemRead...], "total_count":N, "has_more":bool}` |
| 详情 | JSON | `PictureRead` 的 dict |

> 附带修复：`service._list()` 原返回 `count`，但 `fastcrud.paginated_response` 读 `total_count`，导致响应 `total_count` 恒 0。已统一为 `total_count`。

## 五、TTL 策略与热key探测

### 5.1 差异化 TTL

| 数据 | L1 TTL | L2 TTL | 理由 |
|---|---|---|---|
| 详情 | 60s | 300s | 天然热点，变更少 |
| `sort=time` 列表 | 60s | 300s | 新增图片才变 |
| `sort=popularity` 列表 | 30s | 30s | `download_count` 高频变化 |
| `my`/`manage` 私有列表 | — | 默认不缓存 | 权限敏感 + 实时性 |

### 5.2 热key探测（惰性计数提升）

1. 读详情时对 `pic:hot:{id}` 执行 `INCR` + `EXPIRE window`（复用 `rate_limit` 的 Redis pipeline 写法）。
2. 计数 ≥ 阈值（默认 `10` 次/`60s` 窗口）→ `promote_to_local` 将详情从 Redis 提升到 L1，`logger.info` 打点。
3. 提升后后续读命中 L1，不再回源 L2/DB。

## 六、统一缓存管理接口 CacheManager

`TwoLevelCacheManager`（`backend/src/infrastructure/cache/two_level.py`），方法（snake_case）：

- `get(key)` — L1 → L2 穿透；命中 L2 回填 L1；两级都 miss 返回 None
- `put(key, value, ttl)` — 同时写 L1（本地 TTL）与 L2（精确 TTL）
- `evict(key)` — 同步清除 L1 + L2
- `invalidate_by_prefix(prefix)` — 按前缀批量失效（L1 遍历、L2 SCAN）
- `get_or_load(key, loader, ttl, *, track_hot=False)` — 缓存穿透保护；per-key `asyncio.Lock` 防击穿
- `record_access(key)` / `is_hot_key(key)` / `promote_to_local(key)` — 热key探测三件套
- `stats()` — 返回 local/redis 各自 hit/miss/hit_rate

## 七、工程化

- **缓存拦截**：`@cached(key_prefix, ttl, key_builder, track_hot)` 方法级装饰器（`method_cache.py`），内部 `get_or_load`；`ttl` 支持 callable 按参数动态计算。
- **一致性**：写操作后 `_invalidate_picture_cache(picture_id)` → `evict(detail)` + `invalidate_by_prefix("pic:list:")`；`download` 只 evict 详情（popularity 列表靠短 TTL 自愈）。
- **降级**：Redis 异常全部 fail-open（吞异常 + `logger.warning(extra={"reason": "redis_unavailable"})`）。
- **监控**：`GET /api/v1/cache/stats`（仅管理员）返回命中率统计。

## 八、配置项设计

`settings.py` 新增 `TwoTierCacheSettings`（UPPER_SNAKE_CASE，`config(...)` 读取）：

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `CACHE_TWO_TIER_ENABLED` | `true` | 二级缓存全局开关 |
| `CACHE_LOCAL_MAXSIZE` | `1000` | L1 最大条目数 |
| `CACHE_LOCAL_TTL` | `60` | L1 默认 TTL（秒） |
| `CACHE_HOT_KEY_THRESHOLD` | `10` | 热key阈值（窗口内次数） |
| `CACHE_HOT_KEY_WINDOW` | `60` | 热key统计窗口（秒） |

Redis 连接复用现有 `CACHE_REDIS_*`。开关关闭时 `@cached` 直通 DB。
